# JINJU FAULT INSIGHT V3

**기존 운영 앱을 새 디자인으로 바꾸고, 일별 OOS·RAW 이력을 계속 보관하는 첫 구현 버전입니다.**

## 적용 순서

1. 압축을 풉니다. 폴더 내부의 파일과 `.github`, `.streamlit` 폴더를 **기존 운영 저장소 `ons-jinju/260527_-`의 최상위**에 올립니다. 상위 폴더째 올리지 마세요.
2. 기존 `app.py`는 새 `app.py`로 교체합니다. 다른 파일도 함께 올립니다. 엑셀과 기존 `alarm_history.json`은 삭제하거나 교체하지 마세요.
3. 커밋 후 **Actions → Preserve fault history V3**가 초록색 성공인지 확인합니다. 첫 실행에는 원본 분석·이력 생성·원본 보관이 필요합니다.
4. 성공 후 `data/v3/current.json`, `data/v3/events.json.gz`, `data/v3/raw_events.json.gz`, `archive/`가 생성됐는지 확인합니다.
5. 기존 Streamlit 앱의 진입 파일은 그대로 `app.py`입니다. 새 화면이 자동 반영되지 않으면 앱 관리에서 재시작합니다.
6. 첫 화면의 기준일·금일 건수와 **원본 · 저장 상태** 메뉴의 기존 이력 인식 건수를 확인합니다.

### 매일 할 일

기존 파일 **`26년_진주품질개선팀_고장_RAW_DATA.xlsx`**를 같은 이름으로 교체하고 Commit합니다. Actions 성공 후 기준일을 확인합니다. 엑셀은 코드와 별도이며 이 ZIP에는 넣지 않았습니다.

원본 파일이 저장소 최상위에 없을 때만 `data/daily.xlsx`도 지원합니다. 두 위치를 섞지 마세요. 둘 다 있으면 기존 최상위 파일이 우선입니다.

### Actions가 실패할 때

- `Settings → Actions → General → Workflow permissions`에서 워크플로의 쓰기 권한을 사용할 수 있는지 확인합니다. 조직 정책으로 제한되면 관리자의 조치가 필요합니다.
- 오류를 해결한 뒤 **Run workflow**로 다시 실행합니다. 과거 이력 파일을 지우지 마세요.
- 첫 데이터 생성 전에는 준비 안내가 보입니다. 이미 생성된 자료가 있으면 실패 시 이전 자료가 계속 표시될 수 있으므로 기준일을 확인합니다.
- 작업이 겹치더라도 중간 업로드를 놓치지 않도록, 설치 이후 엑셀을 수정한 커밋들을 순서대로 다시 확인합니다. Git 이력을 강제 변경하거나 파일 변경 커밋을 삭제하면 이 복구 경로를 사용할 수 없습니다.

| `data/v3/manifest.json` | 원본 보관 버전 목록 |

| `data/v3/git-sync.json` | 처리 완료한 원본 커밋 목록 |

- 같은 파일을 그대로 재처리하면 원본 보관 개수와 고장 발생 횟수는 늘지 않습니다.
- **같은 발생이 5일 보이면 OOS 발생 1건, 관측일수 5일**입니다. 같은 PORT라도 발생시각이 다르면 별도 발생입니다.
- 하루에 자료가 바뀌면 수정본과 이전 원본 모두 남습니다.
- 기존 이력은 삭제하거나 덮어쓰지 않습니다. 파일이 손상됐으면 중단합니다.
- 원본 엑셀에는 조회에서 제외한 13시 알람 공유 시트도 원본 보존을 위해 그대로 남지만, 화면에서는 노출하지 않습니다.

## 기존 이력 연결

저장소의 다음 파일을 자동으로 읽습니다.

1. `alarm_history.json`
2. `data/alarm_history.json`
3. `data/previous_alarm_history.json`

원본별 사본을 보존합니다. 같은 날짜·PORT에 값이 충돌하면 앞선 파일을 우선하고 알림을 표시합니다. 날짜·PORT가 하나의 OOS 발생만 가리킬 때 연결하며, 근거는 **구이력 날짜/PORT · 발생시각 미검증**으로 구분합니다. 같은 날짜·PORT에 여러 발생이 있으면 임의로 배정하지 않습니다.

`_ports`의 날짜 없는 알람은 보존하지만 다른 발생에 소급 배정하지 않습니다. OOS 행 없이 알람명만 남은 과거 자료도 사본으로 보존하며, 발생시각을 만들어 고장 건수에 포함하지 않습니다. 이미 교체되어 별도 보관이 없는 과거 RAW 전체를 복원하는 기능은 아닙니다.

## 알람 매칭과 분석 기준

- 기존 대표 알람 우선순위와 PORT 정확 일치 → 부분 일치 → DU 조회 흐름을 유지합니다.
- **AAU 매핑 오류 수정:** 실제 첨부 엑셀의 `NodeId / NRCellDUId / RF_port` 열 이름을 사용합니다. 예전의 열 위치 4·5·6은 현재 AAU 구조와 맞지 않았습니다.
- RRU는 `NodeId / EUtranCellFDDId / RF_port`를 사용합니다.
- 부분 일치는 검토 표기를 붙입니다. 매칭이 없으면 OOS Link·세부알람을 참고합니다.
- 금일 RAW를 과거의 다른 OOS 발생에 소급하지 않습니다. `Service Unavailable`은 기존 규칙대로 대표 알람 매칭에서 제외하지만 RAW 원본·누적 기록에는 보관합니다.
- 신규 PORT와 점검·조치 기재는 중복될 수 있습니다. 신규 PORT는 '직전 자료에 없던 PORT'이며 재발 횟수와 다릅니다.
- OOS 순위는 발생별 **최초 확인 대표 알람**을 사용합니다. 이후 알람이 바뀐 사실도 누적 이력·원본에서 확인할 수 있습니다.
- 구 이력의 미검증 알람은 기본 순위에서 제외하며 옵션으로 포함합니다. 이 옵션은 실제 OOS 발생 총수에는 영향을 주지 않습니다.
- RAW 순위는 중복 관측을 제거한 원본 기록 기준입니다. 발생/해제 메시지를 포함할 수 있어 OOS 고장 발생 건수와 동일하지 않습니다.
- 복구시각이 유효하면 복구, 금일 OOS에 있으면 미복구 관측, 없으면 금일 미관측·복구 추정으로 표시합니다. 미관측을 확정 복구로 단정하지 않습니다.
- 식별자·기준일·발생시각이 없거나 비정상인 행은 집계에서 제외하고 원본과 제외 내역을 보관합니다. 기준일은 실행일보다 30일 이상 미래인 값도 제외합니다. RAW의 eventTime은 내보낸 시간이 아닌 원래 발생시간이므로 오래됐다는 이유로 제외하지 않습니다.

## 느려짐을 줄인 방식

- 엑셀 읽기·매핑·중복 제거·이력 저장은 **업로드 시 Actions에서 처리**합니다. 화면을 열 때는 실행하지 않습니다.
- 앱은 GitHub에 이력을 쓰거나 외부 HTTP 요청을 하지 않습니다. 별도 GITHUB_TOKEN을 앱에서 사용할 필요가 없습니다. 기존 Secret을 삭제할 필요도 없습니다.
- 첫 화면에는 가공된 최신 JSON만 읽습니다. 첨부 자료 검증 시 약 62KB였고 원본 엑셀은 약 7.3MiB였습니다.
- 누적 OOS·RAW는 압축 저장하고 해당 메뉴에서만 읽습니다. 표는 100행씩 전송합니다.
- CSV 생성과 보관 원본 읽기는 사용자가 다운로드 준비를 눌렀을 때만 수행합니다.
- Streamlit 절전 해제, 배포 재시작, 네트워크 대기시간 자체를 제거하는 기능은 아닙니다.
- 보관 원본은 삭제 없이 쌓이므로 저장소 용량은 증가합니다. 장기 운영에서는 원본 보관을 별도 저장소로 옮기는 확장 작업이 필요할 수 있습니다. 화면용 자료와 보관 원본을 분리해 이후 전환할 수 있게 했습니다.

## 로컬 실행

```bash
python -m pip install -r requirements.txt -r requirements-build.txt
python build_data.py --source "엑셀_파일_경로.xlsx"
python -m streamlit run app.py
```

저장소를 통한 자동 처리는 `python sync_history.py`입니다. 처리 실패 시 기존 데이터를 지우고 재생성하는 방식으로 해결하지 마세요.
